# i18n

How every user-facing string in this system gets to the person reading it, in the language they read.

The rules are CLAUDE.md invariants 19, 20 and 21. This file is how they are implemented, and why the implementation is shaped the way it is.

Built at build-order step 6, **before the first screen**, for the reason in `docs/DECISIONS.md` D34: retrofitting i18n is not a mechanical job. It is where you find that a string was assembled from fragments, or interpolated mid-sentence in a way Hindi word order will not take. Doing it after the product master means several hundred strings written the wrong way and a lint rule whose first run is a wall of failures nobody has time to read.

---

## The short version

```ts
import { createLanguageSession } from '@ssbazar/shared';

const { t, language, fonts } = createLanguageSession({
  employeePreference, // employees.preferred_language
  storeDefault,       // app_settings.default_language
});

t('cli.catalogue.dry_run_note');            // → "dry run — nothing was written"
t('cli.migrate.done', { count: 3 });        // → "done: 3 migrations applied"
```

There is no other way to produce text. `npm run lint` fails the build on a string literal that reaches a person, and `TranslationKey` fails the compile on a key that does not resolve.

## Where things live

| | |
|---|---|
| `packages/shared/src/i18n/locales/en.json` | Every English message. The source of truth. |
| `packages/shared/src/i18n/locales/hi.json` | Every Hindi message. Same keys, always. |
| `packages/shared/src/i18n/` | Translator, language resolution, plurals, fonts, `COALESCE` in TypeScript |
| `server/src/i18n/language.ts` | Reading the two settings out of Postgres |
| `server/src/i18n/sql.ts` | `COALESCE(name_hi, name)` in SQL |
| `server/src/cli/output.ts` | The only place a CLI writes to a console |
| `tools/eslint-plugin-ssbazar/` | The lint rule |
| `assets/fonts/` | Noto Sans Devanagari, and why it is committed |

**One catalogue for the whole monorepo**, not one per app. The counter, the office and the server CLIs share a vocabulary — a product, a barcode, a tax slab, a rejected row — and three copies of it become three different Hindi words for "barcode" within a month. Ownership is by namespace (`cli.*`, `error.*`, `catalogue.*`) instead.

## Two guarantees, and neither can do the other's job

**The lint rule catches a string that was never externalised.** `ssbazar/no-hardcoded-strings`, an error, so the build fails.

**The type system catches a key that does not resolve.** `TranslationKey` is derived from the shape of `en.json`, so `t('cli.migrate.dnoe')` does not compile.

A rule alone would let you write `t('a.key.i.just.made.up')`. Types alone would let you write `console.log('Nothing to do')`. Both are needed.

### What the lint rule actually looks at

Not "every string literal" — that would flag SQL, column names, error codes and CSS classes, and would be switched off within a week. A switched-off rule is worse than no rule, because it still looks like coverage on the CI page.

It asks a narrower question: **does this text reach a person?** Text reaches a person through a small, enumerable set of exits, and those are what the rule watches:

- an argument to `console.*` or `process.std*.write`
- an argument to the project's own pass-through printers, `output.line` and `output.plain`
- JSX text, and JSX attributes that render as words — `title`, `placeholder`, `aria-label`, `label`, `alt`

It resolves a plain `const` back to its initialiser, one hop. That single hop is what caught step 5's three `const USAGE = '…'` blocks, and it is the difference between a rule that works on real code and one that is defeated by naming a string.

Allowed at a sink: a translator call, and a string with no letters in it at all — `''`, `'  '`, `'---'`, `': '`. Padding and separators are layout, not language.

Getting out of it is ESLint's own directive, with a reason:

```ts
// eslint-disable-next-line ssbazar/no-hardcoded-strings -- brand name, never translated
```

There is deliberately no bespoke escape hatch. A second mechanism is one more thing a reviewer has to know, and `--report-unused-disable-directives` already cleans up after this one.

## Which language a person gets

One chain, in `resolveLanguage`, and every machine uses it:

```
employees.preferred_language  →  app_settings.default_language  →  'en'
```

Every step is allowed to be absent or wrong, and **resolution never throws**.

`preferred_language` is nullable by design — most staff never open the setting. `default_language` lives in `app_settings.value`, which is TEXT holding every setting in the system, so nothing at the database level stops it holding `''`, `'EN'`, `'english'`, or a typo somebody made at eight in the evening. An unreadable value is not an error worth stopping a sale for; it is a reason to fall through. The last step is a constant, which is what makes the chain total.

`parseLanguage` tolerates case and surrounding whitespace and nothing else. `'hindi'` and `'hi-IN'` are refused rather than guessed at — quietly accepting them is how a value nobody can explain ends up in the database and outlives the person who put it there.

### Offline

The counters bill through a server outage. That is their whole job, so the language cannot come from a query that may not answer:

- **Apps** resolve from the local SQLite cache's mirror of the two settings. `createLanguageSession` takes values, not a database handle.
- **CLIs** use `resolveLanguageFor`, which reads `app_settings` when there is a connection and falls back to `SSBAZAR_LANG` and then English when there is not. `db:migrate` prints "could not reach Postgres" in exactly the situation where the settings table is unreachable, so this is not a hypothetical.
- **`--lang=en|hi`** on any CLI outranks everything, which is also how a support call reproduces what the client saw without editing his settings.

## Writing a message

Nest by area. Use `{name}` for anything variable:

```json
"cli": {
  "catalogue": {
    "rows_read": { "one": "{file}: {count} data row", "other": "{file}: {count} data rows" },
    "unreadable": "the file could not be read: {detail}"
  }
}
```

**Never assemble a sentence from pieces.** `t('applied') + ' ' + filename` produces English word order in a Hindi string, and the two languages do not agree about where the verb goes. Put the whole sentence in the catalogue with a placeholder in it. This is the failure D34 predicted and the reason the rule flags a template literal whose fixed parts contain letters.

### Plurals

A message with a count takes `one` and `other`. English and Hindi have the same two CLDR categories but *not* the same rule for choosing between them:

| count | en | hi |
|---|---|---|
| 0 | other | **one** |
| 1 | one | one |
| 2 | other | other |
| 0.5 | other | other |

Hindi's `one` covers `i = 0..1`: zero takes the singular. Getting this wrong is not a crash — it is a line that reads slightly wrong on every report, forever, and nobody files a bug about it.

### When a key is missing

`hi.json` falls back to `en.json`, key by key. That mirrors invariant 20 at the string level: Hindi is allowed to lag exactly as `name_hi` is allowed to be NULL.

It should never happen in a shipped build and it cannot happen by accident — `catalogue.test.ts` asserts that both files hold the same keys, the same plural forms, and the same placeholders. The placeholder check is the one that earns its place: a Hindi sentence that dropped `{count}` reads perfectly and is simply missing the number.

A key that resolves in neither language comes back as itself. `t` does not throw, ever. It is on the path of every line of every receipt, and a translator that threw would take the till down over a typo in a file nobody compiles, in the middle of the evening rush.

## Errors carry keys, not sentences

Established at step 2 and resolved here. An error a person will read carries a key and its parameters:

```ts
throw new TaxInputError('line.qty_invalid', { line: 3 });
// message: "Line 3: quantity must be more than zero."   ← from en.json, not written here
```

`TranslatableError` fills `Error.message` from the English catalogue, so a stack trace still reads properly without any English being written in the module. The UI calls `t(error.messageKey, error.params)` and gets Hindi.

`TaxErrorCode` values are deliberately the tail of their own keys — `bill.no_lines` → `error.tax.bill.no_lines` — so `taxErrorKey` is the whole of the mapping, and **adding a code without adding its message does not compile**. That is the check worth having: the failure it prevents, an English sentence at a Hindi terminal, only shows up on the day a bill will not total.

The importer works the same way. `RowIssue` carries `reasonKey` and `reasonParams`, never a sentence, which is what lets one validator serve `catalogue:import` at a terminal today and the import screen in step 7 without either owning the English.

### Where the line is

Not everything gets translated, and the test is **who reads it**.

A cashier or the shop owner reads "this barcode is already on a product" — that is translated. Whoever is installing the system reads "migration 004 has changed since it was applied" — that is not. `MigrationPlanError` messages name filenames and checksums, are read in the same session as a stack trace, and translating them buys nothing. They arrive at the CLI as detail and are passed through as detail inside a translated sentence.

Also deliberately untranslated:

- **Command-line flags.** `--dry-run` is typed back character for character. A Hindi build that renamed it would print instructions that do not work.
- **Column names in the import report.** They are the headings in the client's own spreadsheet.
- **Check keys** like `stock_on_hand`. A support call goes better when both ends say the same string.
- **Statutory acronyms** — GST, CGST, HSN, MRP.

## Product names: `COALESCE(name_hi, name)`

Invariant 20 and D20. Hindi columns are nullable and fall back to English when blank, so the client fills the few hundred items that matter rather than doubling his catalogue data entry — which is already the longest pole in the project.

The fallback has to exist in two places and they are not interchangeable:

**In SQL** — `server/src/i18n/sql.ts` — when Postgres is selecting, sorting or searching. A list sorted by `name` and displayed as `name_hi` comes back in an order the eye cannot follow: the customer asks for आटा and the row is filed under "Atta" three screens away. The sort key has to be the string being shown.

**In TypeScript** — `localisedText` — when a row is already in hand. The counters' offline cache holds both columns, and the receipt renderer needs `name_hi` separately anyway.

Both use `NULLIF(btrim(…), '')` rather than a bare `COALESCE`. An imported spreadsheet produces an empty cell far more often than it produces NULL — a column somebody tabbed through — and a product whose Hindi name is one space prints as nothing at all on a raster receipt.

Not a view or a generated column, tidier though that would be: the expression depends on who is looking. `display_name` cannot be one stored column when the same row is Hindi for one cashier and English for the next.

## The font

`assets/fonts/NotoSansDevanagari-{Regular,Bold}.ttf`, SIL OFL 1.1, hinted TTF. `assets/fonts/README.md` has the provenance and hashes; paths come from `devanagariFont()` so there is one answer to "which file".

Committed rather than fetched or taken from the operating system: the shop machines go days without internet, and what is installed on a Windows machine in a shop is not something this project controls — the same bill would print differently on each counter.

Hinted, and a full TTF rather than a web subset, both for the printer rather than the screen. Receipts print at 203 dpi on a 576-dot line, where Devanagari is a handful of pixels per glyph and hinting is what keeps a matra from disappearing into the stroke below it. And the `GSUB`/`GPOS`/`GDEF` tables are not optional: Devanagari is not a script you can lay out left to right and be done with — conjuncts substitute, matras reorder around the consonant they attach to, and `GSUB` is the table that says so. Text shaped without it renders, which is exactly why `fonts.test.ts` checks for those tables rather than trusting a glance.

### Raster mode

Invariant 21: a receipt renders as a bitmap **only when a line carries a Hindi name**. `needsDevanagari(language, lines)` is that question, and note what it is not — it is not "the language is Hindi". A Hindi-speaking cashier ringing up items that have no `name_hi` prints entirely in Latin and must stay in fast text mode. Raster costs 3–4 seconds a bill, which at 1,000 bills a day is about an hour of queue time concentrated in the evening rush.

The printing module itself lands later. The font is here first because it is the part with a licence to check and a provenance to record.

## Adding a string

1. Add the key to **both** `en.json` and `hi.json`. Same path, same plural forms, same placeholders — the tests check all three.
2. Call `t('your.key', { … })`. If it does not compile, the key is wrong.
3. `npm run check`.

If you are adding a string and there is genuinely no Hindi for it yet, add the key to both files anyway with the English text in `hi.json` — and expect `catalogue.test.ts` to fail, which is the point. It asks for Devanagari in any Hindi entry whose English has three or more words in it, because a Hindi entry that is still the English sentence is a placeholder somebody meant to come back to and never will.
